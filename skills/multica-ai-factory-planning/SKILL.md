# Multica AI 软件工厂规划

把已确认目标、仓库事实和已批准输入编译为正式基线与可执行的父子 Issue / 阶段图。

## 开始前

1. 完整读取 [执行基线](references/governance-baseline.md)和 [Issue 契约](references/multica-issue-contract.md)。
2. 读取当前规划 Issue、父 Issue、Project 描述、属性、评论、资源和全部声明输入。
3. 读取仓库原生智能体指令、文档地图、相关代码、测试、数据、接口和近期变更。
4. 核对任务类型为 `Planning`、状态为 `todo`、负责人、依赖、已批准输入和验收。
5. 就绪条件成立时设为 `in_progress`；否则记录阻塞并设为 `blocked`。
6. 读取“自动推进”章节；`autonomous` 模式必须能够识别协调父 Issue 和编排 Agent。

`todo` 不代表平台已经验证依赖。开始产出前按 Issue 正文逐项核验所有 `hard` 依赖；不得自行豁免、解除依赖或把 `cancelled` 当作 `done`。

## 选择规划模式

声明一种：

- 新项目或新能力；
- 已批准能力的增量变更；
- 缺陷诊断；
- 架构/技术债治理；
- 部署或运行能力规划。

## 建立事实基线

明确区分：

- 人工已确认业务决定；
- 当前已批准文档；
- 仓库已实现事实；
- 待验证假设。

用文件、提交、日志、接口、数据模型、运行结果和测试支持结论。文档与代码不一致时记录差异，不静默选择一方。

缺陷诊断必须给出复现条件、证据链、根因置信度、影响范围和候选修复；证据不足时保持不确定结论。

## 做影响分析

覆盖适用项：

- 产品范围、用户和权限；
- 数据、接口、并发和兼容；
- 前端、交互和可访问性；
- 架构、安全、隐私和可观测性；
- 迁移、部署、回滚和运行；
- 单元、接口、集成、E2E、视觉和回归测试。

## 更新正式产物

只在 Issue 授权范围内创建或修订：

- 当前分析和文档地图；
- PRD 与验收口径；
- UX 输入约束；
- 架构、接口、数据和 ADR；
- 迁移、兼容、回滚和测试要求；
- 阶段任务图与下游 Issue 草案。

尊重仓库既有文档结构。修改已批准文档时创建新版本，旧版本标为 `Superseded`（已替代）。

## 处理设计分支

包含新页面、关键交互、视觉状态、响应式要求或 Figma 变化时，建立独立设计 Issue。设计与架构可以并行，但开发前必须完成交叉一致性和相应审计。

## 生成阶段任务图

1. 按可独立验收与责任边界拆分子 Issue。
2. 明确任务类型、阶段、共享契约和集成点；每条依赖写明前置 Issue key/文档、必需状态/版本、`hard` 类型和满足证据。
3. 为开发建立对应 QA 和审计门禁；需要部署时建立发布 Issue。
4. 建立依赖矩阵或邻接表，检查无孤儿、无自依赖、无缺失节点、无循环、无无法验收的大 Issue；显式标注跨 Project/工作区依赖。
5. 下游 Issue 默认 `backlog`；只有当前获准阶段且完全就绪时才可设为 `todo`。
6. 声明 Issue 正文为当前依赖权威来源、Stage 仅为分组和唤醒；不得假设平台存在自动硬依赖门禁。

创建/更新下游 Issue 是写操作，必须由当前规划 Issue、人或采用 `autonomous` 的协调父 Issue 明确授权。

## 交付

- 核对需求—设计—架构—Issue—测试的双向追溯。
- 记录产物路径、版本、调查证据、验证结果、风险和未决决定。
- 先发布最终交付评论，再将规划 Issue 设为 `in_review`。
- `autonomous` 模式下，在最终评论中 mention 协调编排 Agent，指明需要启动的需求、架构或任务拆解 Audit、固定候选、PASS/FAIL 路径，并标记“是否需要人工操作”。
- 只有确实存在业务选择、重大架构取舍、数据/合规决定或风险接受时才标记需要人工操作；不得把例行规划评审推给人。
- 不实现生产代码，不把自身 Issue 设为 `done`。

## 输出

1. 规划模式和就绪结论；
2. 仓库事实、证据和差异；
3. 新建/修改文档及状态；
4. ADR 和关键取舍；
5. 阶段任务图、显式依赖与下游 Issue；
6. 验证、风险、未决业务决定；
7. 建议状态、下一门禁、编排 Agent mention 和是否需要人工操作。
