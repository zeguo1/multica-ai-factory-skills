# Multica AI 软件工厂设计

把已批准的产品语义转化为开发 Agent 可实现、QA 可验证、审计 Agent 可追溯的 UX/UI 基线。

## 开始前

1. 完整读取 [执行基线](references/governance-baseline.md)和 [Issue 契约](references/multica-issue-contract.md)。
2. 读取设计 Issue、父 Issue、Project、已批准 PRD、架构约束、现有设计系统、前端实现和 Figma。
3. 核对任务类型为 `Design`、状态为 `todo`、依赖、目标终端、品牌资产、工具权限和验收。
4. 就绪条件成立时设为 `in_progress`；否则记录阻塞并设为 `blocked`。

## 建立体验约束

- 明确用户、场景、主任务、成功路径、失败路径和边界条件。
- 区分产品规则与表现方式；新增业务规则必须退回规划 Agent 或人确认。
- 核对数据和接口约束，不设计系统无法表达的隐含状态。

## 设计完整状态

覆盖适用项：

- 首次、正常、空、加载、失败、无权限、离线、超时和部分成功；
- 表单校验、重复提交、撤销/恢复和危险操作确认；
- 不同角色、数据范围、语言和设备尺寸；
- 长文本、溢出、滚动、键盘、焦点、对比度和可访问性；
- 既有设计系统组件、变量和交互模式。

## 形成交付

按 Issue 授权交付：

- 用户流和信息架构；
- 页面/组件清单；
- 状态矩阵和交互规则；
- 响应式布局和断点；
- 设计系统变量、组件和变体；
- Figma 页面、节点和原型链接；
- 开发 Agent 与 QA 的可验证设计清单。

Figma 工具不可用时可以先完成 Markdown 规格；Issue 明确要求 Figma 时，该交付仍为阻塞项，不能声称完成。

## 做一致性检查

逐项核对已批准 PRD、架构、接口/数据、现有组件和测试可观察性。记录冲突、责任人和影响门禁，不自行改写上游决定。

## 交付

- 记录设计产物、版本、Figma 节点、状态覆盖和一致性结论。
- 将设计 Issue 设为 `in_review`。
- 指明 UX 审计、交叉一致性和人工视觉/关键交互批准。
- 不实现生产 UI，不把自身 Issue 设为 `done`。

## 输出

1. 就绪结论和输入版本；
2. 用户流、页面与完整状态覆盖；
3. 设计产物及版本；
4. Figma 或替代规格位置；
5. PRD/架构一致性；
6. 开发/QA 验收清单；
7. 风险、未决项和下一门禁。
