# AI 软件工厂 Multica 执行基线 V3.2

本文件是 Agent 执行摘要。V3.2 在保留独立 QA / Audit 门禁的同时，增加显式启用的自治编排。完整治理以项目已批准的 V3.2 规范、项目已批准基线和仓库原生规则为准。

> 机器标识约定：Multica 状态值、CLI 命令、Skill 名和 `Planning` 等任务类型枚举保留英文；其余说明使用中文。

## 1. 事实来源

1. 人工明确批准的业务决定、风险接受和生产发布批准是最高业务事实。
2. 当前已批准的 PRD、UX、架构、ADR、测试和发布文档定义项目语义。
3. 仓库的 `AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING.md`、构建文件和包级规则定义工程执行约束。
4. Multica Project 和 Issue 定义当前工作、责任、状态、阶段和证据。
5. 工作区 Skill 定义角色方法；Task/Run 只记录单次执行。
6. 会话、模型记忆和未批准草稿不得覆盖上述来源。

冲突无法按职责边界消解时，发表评论说明证据，将 Issue 设为 `blocked`，等待责任人裁决。

## 2. Multica 术语

- Issue：持续存在的工作记录。
- 子 Issue / 叶子 Issue：可独立领取和验收的工作项。
- Task/Run：一次 Agent 执行，不是规划层级；`completed` 不等于 Issue 完成。
- `backlog`：停放并等待输入、依赖或门禁；在自治模式中不代表需要人规划。
- `todo`：已就绪，已分配 Agent 时可能立即创建 Task/Run。
- `in_progress`：正在处理。
- `in_review`：产物已提交，等待或正在执行独立 QA / Audit；除非明确标记“需要人工操作”，否则不要求人审核。
- `blocked`：无法继续，必须记录责任人、解除条件和是否需要人工决定。
- `done`：全部适用门禁满足，由人或已获授权的编排 Agent 自动设置。

## 3. 角色边界

| 角色 | 负责 | 不得代替 |
| --- | --- | --- |
| 人 | 商业决定、范围批准、风险接受、生产发布批准 | Agent 的证据核验 |
| 编排 Agent | 需求收敛、分类、父子 Issue 与阶段协调 | 正式基线、代码、QA / Audit 结论 |
| 规划 Agent | 仓库调查、PRD、架构、ADR、诊断、任务图 | 业务决定、生产代码、自行批准 |
| 设计 Agent | UX、UI、状态、设计系统、Figma | 改变产品规则、实现生产代码、自行批准 |
| 开发 Agent | 实现、自测、PR、实现证据 | 独立 QA / Audit、直接完成、发布 |
| QA Agent | 独立验证用户行为和质量 | 修改被测实现、审计、发布批准 |
| 审计 Agent | 固定版本的一致性与证据审计 | 整改被审计产物、业务取舍 |
| 发布 Agent | 明确环境中的部署、验证、回滚 | 绕过 QA / Audit / 人工批准 |

生产者不能担任同一候选版本的最终 QA 或 Audit。平台技术权限不等于治理授权。

## 4. 主流程与门禁

```text
目标确认
→ 规划（Planning）
→ PRD / UX / 架构 / ADR / 阶段任务图
→ G1-G3 审计与必要的人工批准
→ 开发（Development）
→ QA + 代码审计
→ G4
→ 发布（Release）
→ G5 + 人工生产批准
```

- G1：需求审计 PASS + 存在业务选择时的关键范围人工批准。
- G2：UX / 架构审计 PASS + 交叉一致性 + 存在重大取舍时的人工批准。
- G3：任务拆解审计 PASS，才可把开发 Issue 提升为 `todo`。
- G4：QA PASS + 代码审计 PASS + 证据完整。
- G5：发布审计 PASS + 当前候选版本人工批准 + 可执行回滚。

## 5. 阶段与依赖

1. 当前阶段使用 `todo`，后续阶段使用 `backlog`。
2. 同一阶段内可以并行，但必须有清晰的修改和验收边界。
3. 阶段完成会唤醒父 Issue 负责人；启用自治模式时，编排 Agent 必须核验门禁并自动推进满足条件的下一阶段。
4. Stage 只是分组与唤醒屏障，不代表依赖已经满足，也不自动改变子 Issue 状态。
5. 当前 Multica 没有可由本流程依赖的 Issue 硬依赖 API/UI；Issue 正文“依赖与阶段”是依赖关系的权威来源，由编排 Agent 执行软门禁。任何角色不得假设平台会自动阻止未就绪 Issue 执行。
6. 每条前置依赖必须声明：前置 Issue key 或文档、必需状态/版本、依赖类型、满足证据；无依赖时明确写“无”。
7. `hard` 依赖未满足时，未开始的 Issue 保持 `backlog`；执行中发现缺失或失效时，先记录阻塞，再设为 `blocked`。
8. 只有编排 Agent 或明确授权的人可以在逐项核验全部 `hard` 依赖、已批准输入和门禁后，将 Issue 提升为 `todo`。自治模式下这是编排 Agent 的必需职责，不得把例行推进留给人处理。执行角色不得自行解除依赖或提升状态。
9. `done` 默认满足要求为 `done` 的依赖；`cancelled` 默认不满足，只有具备批准人、理由、时间、影响范围和证据链接的人工豁免才可视为满足。
10. 依赖图必须无自依赖、无循环、无缺失节点。跨 Project 或跨工作区依赖必须显式标注并证明可读取、可追溯。
11. 依赖变更必须重新检查所有下游 Issue；受影响的 `todo`、`in_progress` 或 `in_review` Issue 在重新通过 Ready 检查前不得继续推进。

## 6. 状态权限

- 规划、设计、开发 Agent：交付后最多设置为 `in_review`，并在最终评论中通知协调父 Issue 的编排 Agent。
- QA、审计 Agent：提交 PASS / FAIL，不直接把被测或被审计 Issue 设为 `done`；最终评论必须通知编排 Agent 接棒。
- 发布 Agent：只操作 Issue 明确授权的环境。
- `done`：自治模式下由编排 Agent 在适用 PASS、候选一致性和必要人工决定全部满足后设置；不再要求人逐项点击确认。
- `blocked`：评论记录事实、影响、责任人、解除条件和下一次检查条件。

## 7. 自治编排与人工边界

1. Project 或协调父 Issue 必须显式声明 `自动推进模式：autonomous` 才启用自治推进；未声明时保持人工模式，避免静默改变既有项目。
2. 技术叶子 Issue 必须隶属于由编排 Agent 负责的协调父 Issue，或明确填写协调 Agent。不得留下无人接棒的根级 Planning / Development Issue。
3. 规划、设计、开发、QA、审计和发布 Agent 交付时，先发布结构化结果评论，再把自身 Issue 设为 `in_review`，并使用 Multica Agent mention 通知编排 Agent。
4. 编排 Agent 被通知后必须读取固定候选和证据，创建或启动下一门禁；PASS 时关闭已通过的门禁 Issue 和被审核 Issue，FAIL 时退回原责任角色整改并使旧候选结论失效。
5. 只有以下情况要求人参与：业务规则或范围选择、无法从证据确定的数据/合规决定、重大风险接受、生产发布批准、不可逆或破坏性操作授权。普通规划评审、代码评审、QA、Audit 和非生产推进不要求人逐项确认。
6. 需要人工参与时，编排 Agent 将 Issue 设为 `blocked` 或保持安全停放，发布标题为“待人工决定”的结构化评论，列出选项、建议、影响和解除条件；不得只写“等待确认”。
7. 若无法找到协调 Agent、mention 失败或下一门禁 Issue 缺失，当前 Issue 不得无声停在 `in_review`；必须记录“自动接棒失败”并通知可识别的负责人。

## 8. PR 与证据

- PR 标题、正文或分支使用 Multica Issue key 建立追溯。
- G4 前不使用 `Closes`、`Fixes`、`Resolves` 加 Issue key，避免合并自动设置为 `done`。
- 必需证据回写 Issue：产物路径、固定版本、命令和结果、PR / Commit、截图或日志、风险、回滚与下一门禁。
- 不把“未运行”或“环境不可用”写成通过。

## 9. 变更与安全

- 修改已批准基线时，先建立变更规划 Issue，暂停受影响工作，更新源文档并重新执行门禁。
- 保护用户已有未提交修改，不执行范围外重构。
- 不执行未授权的外部写入、合并、部署和生产操作。
- 不把密钥写入 Issue、metadata、评论、截图、仓库或 Skill。
- Agent `custom_env` 存在服务器端，只使用有限权限凭据。
