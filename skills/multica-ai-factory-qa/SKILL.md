# Multica AI 软件工厂 QA

独立验证用户可观察行为和系统质量，不把开发者自测、代码阅读或 Task/Run 完成当作 QA。

## 开始前

1. 完整读取 [执行基线](references/governance-baseline.md)和 [Issue 契约](references/multica-issue-contract.md)。
2. 读取 QA Issue、父 Issue、已批准的 PRD/UX/架构/ADR、开发 Issue、自测证据和目标环境。
3. 固定候选 Commit/PR/构建/环境，确认数据、账号、权限、环境健康和验收标准。
4. 核对任务类型为 `QA`、状态为 `todo`、依赖和候选唯一性。
5. 就绪条件成立时设为 `in_progress`；候选漂移或环境不可用时记录阻塞并设为 `blocked`。

## 建立测试矩阵

把每条验收标准映射到测试项，覆盖适用维度：

- 正常、边界、失败和恢复；
- 角色、权限和数据范围；
- API、数据库、消息和第三方集成；
- 回归、兼容和端到端路径；
- UI 状态、响应式、可访问性和 Figma/UX 对照；
- 迁移、回滚、性能、安全与可观测性专项。

## 独立执行

- 在声明环境或可重复本地环境运行。
- 记录候选版本、时间、前置数据、步骤、期望和实际结果。
- 不用开发者结论代替实际验证；可复用可核验的环境准备和测试脚本。
- 不修改业务实现让测试通过。QA 范围内的测试脚本/夹具变更必须与被测代码分开记录。

## 失败处理

每个缺陷记录：严重度、复现概率、前置条件、最小步骤、期望、实际、证据、影响基线和建议责任人。

需求、UX 或架构矛盾退回对应责任角色，不伪装成代码 Bug。

## 结论

- `PASS`：全部强制验收项通过，候选和环境可信，无阻断缺陷。
- `FAIL`：任一强制项失败、关键范围未测或证据不足。

若工作区存在“QA 结论”属性，写入 PASS / FAIL；同时发布结构化结果评论。将 QA Issue 设为 `in_review`，等待门禁执行者确认。不要把开发 Issue 修改为 `done`。

## 输出

```markdown
## QA 结论
PASS / FAIL

## 候选对象
- Commit / PR / 构建 / 环境：

## 覆盖范围
- 验收标准 → 测试 → 结果 → 证据

## 缺陷
- 严重程度 / 复现步骤 / 证据 / 责任人 / 是否阻断

## 未测试范围
- 项目 / 原因 / 影响

## 下一门禁
- 审计、整改或批准
```
