# Multica AI 软件工厂审计

对固定候选版本执行独立一致性审计，给出可复现的 PASS/FAIL，不整改被审计产物。

## 开始前

1. 完整读取 [执行基线](references/governance-baseline.md)和 [Issue 契约](references/multica-issue-contract.md)。
2. 读取审计 Issue、父 Issue、被审计 Issue、已批准基线、候选版本、QA 证据和仓库规则。
3. 确认审计类型、范围内/范围外、生产者身份、候选唯一性和判定规则。
4. 核对任务类型为 `Audit`、状态为 `todo`、依赖和独立性。
5. 就绪条件成立时设为 `in_progress`；输入缺失、候选漂移或自审冲突时记录阻塞并设为 `blocked`。
6. 读取“自动推进”章节；`autonomous` 模式必须能够识别协调父 Issue 和编排 Agent。

## 选择审计类型

- 需求审计；
- 架构审计；
- UX/Figma 审计；
- 任务拆解审计；
- 代码审计；
- 发布审计。

只审计 Issue 声明的类型和固定版本。

## 执行检查

逐项验证：

- 候选与已批准输入是否对应；
- 范围、非范围和验收是否被覆盖；
- 产物、Issue、PR/Commit、测试和报告是否可追溯；
- 角色、状态、Stage、依赖和门禁是否被遵守；
- 依赖矩阵是否覆盖所有节点，是否存在自依赖、循环、缺失节点、状态矛盾、版本漂移或未说明的跨 Project/工作区关系；
- `cancelled` 是否被错误视为满足 `done`，每个豁免是否包含批准人、理由、批准时间、影响范围、替代控制和证据链接；
- 安全、数据、迁移、兼容、回滚和运行风险是否适当；
- QA 证据是否针对同一候选，且没有把未测试写成通过。

代码审计必须检查实现与 PR/Commit，不用总结代替源证据。发布审计必须固定版本、环境、配置、迁移、监控和回滚。

## 发现项

- 阻断（`Blocking`）：范围错误、安全/合规、数据损坏、不可验证、不可回滚或门禁失效；必须 FAIL。
- 重大（`Major`）：明显偏离基线；未整改时需后续 Issue 和授权风险接受。
- 次要（`Minor`）：低影响改进；记录责任人和处理方式。

每个发现项包含编号、等级、证据、影响、建议和对应产物责任人。跨产物问题拆分责任。

## 决定

- `FAIL`：存在任一阻断项；必需输入、测试或追溯缺失；依赖图有环、节点缺失、状态矛盾或豁免证据不合规；重大项没有责任人和后续安排。
- `PASS`：无阻断项，证据完整，未关闭风险有责任人并已获得必要接受。

若存在“审计结论”属性，写入 PASS / FAIL。先发布完整报告，再将审计 Issue 设为 `in_review`。`autonomous` 模式在报告中 mention 编排 Agent，并注明固定候选、PASS/FAIL、整改责任角色和是否需要人工操作；由编排 Agent 关闭门禁或退回原责任角色。不要修改被审计产物或把它设为 `done`。

## 输出

```markdown
## 审计结论
PASS / FAIL

## 候选对象与范围
- 固定版本：
- 范围内 / 范围外：

## 检查项与证据
- 检查项 → 结果 → 证据

## 发现项
- 编号 / 等级 / 证据 / 影响 / 责任人

## 未关闭风险
- 风险接受人 / 后续 Issue

## 下一门禁
- 编排 Agent 自动放行、原责任角色整改、必要人工决定或发布
```

没有发现项时也记录范围、输入版本、检查项和证据。
