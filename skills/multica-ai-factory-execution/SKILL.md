# Multica AI 软件工厂开发执行

在已批准基线、仓库原生规则和 Issue 边界内实现可验证变更，自测和提交评审后停止。

## 开始前

1. 完整读取 [执行基线](references/governance-baseline.md)和 [Issue 契约](references/multica-issue-contract.md)。
2. 读取开发 Issue、父 Issue、Project、已批准的 PRD/UX/架构/ADR、依赖、测试和迁移要求。
3. 读取仓库 `AGENTS.md`、`CLAUDE.md`、构建文件和相关包级规则。
4. 检查仓库、分支/worktree、目标基线和未提交变更，保护用户已有修改。
5. 核对任务类型为 `Development`、状态为 `todo`、G3、依赖、验收和资源。
6. 就绪条件成立时设为 `in_progress`；否则记录阻塞并设为 `blocked`。

`todo` 不代表平台已经验证依赖。修改代码前按 Issue 正文逐项核验所有 `hard` 依赖、必需状态/版本和满足证据；不得自行豁免、解除依赖、提升状态或把 `cancelled` 当作 `done`。

## 建立实现映射

修改前证明真实路径：

```text
入口 → 用户或 Agent 操作 → 组件/API/数据副作用 → 可观察结果
```

把每条验收标准映射到代码位置、测试和证据。Bug 先复现；无法复现时提交证据，不做猜测式修改。

需要改变已批准的产品、架构、数据契约或 UX 时停止，申请变更规划 Issue。

## 实施

- 实施满足主路径、失败处理和验收所需的最小完整变更。
- 遵循仓库现有架构、命名、依赖和测试位置。
- 同步必要迁移、兼容、回滚、日志、监控和实现文档。
- 不添加范围外双写、旧路径兼容层、临时适配层或推测性回退。
- 不覆盖、清理或提交与 Issue 无关的用户改动。

## 自测

按仓库规则、Issue 要求和变更风险运行相关检查，覆盖适用项：

- 新增/修改行为的自动化测试；
- 关键失败、边界和权限；
- 受影响模块回归；
- 迁移与回滚；
- 构建、类型、接口、交互和视觉对照。

环境、凭据或外部服务导致无法运行时，准确记录原因和未验证范围；不得写成通过。

## PR 与候选版本

代码变更默认建立或更新 PR，除非 Issue 明确要求本地交付或无代码变更。使用 Issue key 建立链接：

```text
MUL-123：实现某项功能
```

G4 前不使用 `Closes`、`Fixes` 或 `Resolves` 加 Issue key，避免 PR 合并自动 `done`。不自行合并或发布。

## 交付

- 记录修改文件、行为、候选 Commit/PR、命令和逐项结果。
- 映射验收标准—测试—证据。
- 说明迁移、回滚、风险和未验证范围。
- 将开发 Issue 设为 `in_review`。
- 指明独立 QA 与代码审计。
- 不把自身 Issue 设为 `done`。

## 输出

1. 就绪结论、基线和真实操作路径；
2. 修改文件和行为；
3. 测试命令及结果；
4. 验收—测试—证据映射；
5. PR/Commit；
6. 迁移、回滚和风险；
7. 未验证项；
8. 当前状态与下一门禁。
